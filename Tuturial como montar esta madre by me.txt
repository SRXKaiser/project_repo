¿QUÉ ES PROJECT REPOSITORY?
============================================================

Project Repository es una aplicación web orientada a la gestión de proyectos de investigación.

El sistema está dividido principalmente en:

FRONTEND
BACKEND
BASE DE DATOS


Visualmente:

USUARIO
   |
   | hace clic
   v
FRONTEND
localhost:5173
   |
   | HTTP / JSON
   v
BACKEND - FASTAPI
localhost:8000
   |
   | SQLAlchemy
   v
POSTGRESQL


El frontend es lo que ve el usuario.

El backend procesa las acciones.

PostgreSQL guarda la información.


EJEMPLO:

Un usuario quiere ver los proyectos.

1. El usuario entra a la página.

2. El frontend pide:

   "Dame los proyectos."

3. El frontend hace una petición al backend:

   GET /proyectos

4. FastAPI recibe la petición.

5. FastAPI utiliza SQLAlchemy.

6. SQLAlchemy consulta PostgreSQL.

7. PostgreSQL devuelve los proyectos.

8. FastAPI devuelve los datos en JSON.

9. El frontend muestra los proyectos.


Más o menos:

Usuario
   |
   v
Frontend
   |
   | GET /proyectos
   v
FastAPI
   |
   v
SQLAlchemy
   |
   v
PostgreSQL
   |
   v
SQLAlchemy
   |
   v
FastAPI
   |
   | JSON
   v
Frontend
   |
   v
Usuario ve los proyectos


============================================================
DICCIONARIO PARA PENDEJOS
============================================================

------------------------------------------------------------------------------------------
API (Estoy seguro de que el pobre bastardo que va a documentar no sabe que es una api)
------------------------------------------------------------------------------------------

Es la forma en la que frontend y backend se comunican.

Ejemplo:

GET /proyectos

significa:

"Backend, dame los proyectos."


POST /proyectos

significa:

"Backend, quiero crear un proyecto."


------------------------------
ENDPOINT
------------------------------

Un endpoint es una dirección concreta de la API.

Ejemplos:

GET /proyectos

GET /usuarios

POST /auth/login

GET /departamentos


Cada endpoint hace algo diferente.


------------------------------
FASTAPI
------------------------------

FastAPI es el framework de Python utilizado para crear el backend.

Es quien recibe las peticiones HTTP.

Ejemplo:

Frontend:

"Quiero los proyectos."

FastAPI:

"Ok, voy a buscarlos."


------------------------------
POSTGRESQL
------------------------------

PostgreSQL es la base de datos.

Aquí se guarda la información de forma permanente.

Por ejemplo:

usuarios
proyectos
carreras
departamentos
áreas temáticas
palabras clave
etc.


Piensa en PostgreSQL como un Excel con esteroides y muchísimo más serio.


------------------------------
SQLALCHEMY
------------------------------

SQLAlchemy permite que Python se comunique cómodamente con PostgreSQL.

Sin SQLAlchemy tendríamos que escribir mucho SQL manualmente.

Con SQLAlchemy podemos tener modelos Python.

Ejemplo conceptual:

class Usuario:
    id
    nombre
    email
    password


SQLAlchemy sabe cómo relacionar eso con una tabla de PostgreSQL.


------------------------------
ALEMBIC
------------------------------

Alembic controla los cambios en la ESTRUCTURA de la base de datos.

Es básicamente:

"Git, pero para la estructura de PostgreSQL."

Supongamos que tenemos:

usuarios

id
nombre
email


Pero mañana necesitamos:

usuarios

id
nombre
email
foto_perfil


No queremos decirle a cada desarrollador:

"Entra a PostgreSQL y crea manualmente la columna."

Creamos una MIGRACIÓN.

Alembic aplica esa migración.

Y listo.


------------------------------
DOCKER
------------------------------

Docker crea un entorno controlado donde ejecutar nuestro programa.

Evita situaciones como:

"Yo tengo Python 3.X"

"Yo instalé otra versión"

"A mí me falta una dependencia"

"Pues en mi PC funciona"


Docker básicamente dice:

"Me vale madres qué tengas instalado.
Voy a crear mi propio entorno."


------------------------------
DOCKER IMAGE
------------------------------

Una imagen es como una plantilla.

Dice:

- qué sistema base utilizar;
- qué versión de Python;
- qué dependencias instalar;
- qué archivos copiar;
- qué comando ejecutar.


------------------------------
CONTAINER
------------------------------

Un container es una imagen EJECUTÁNDOSE.

Imagen:

"Así debería ser el backend."

Container:

"El backend está vivo."


------------------------------
DOCKERFILE
------------------------------

El Dockerfile explica cómo construir una imagen.

Nuestro Dockerfile conceptualmente hace:

Python
   |
   v
crear /app
   |
   v
instalar dependencias
   |
   v
copiar backend
   |
   v
ejecutar Uvicorn


------------------------------
DOCKER COMPOSE
------------------------------

Docker Compose coordina varios servicios.

Idealmente nuestro proyecto terminaría teniendo:

docker-compose.yml

   |
   +---- backend
   |
   +---- postgres
   |
   +---- posiblemente frontend


Entonces podríamos ejecutar:

docker compose up

y levantar prácticamente todo.


------------------------------
JWT
------------------------------

JWT significa JSON Web Token.

Se utiliza para autenticación.

Cuando haces login:

email + contraseña
       |
       v
backend comprueba
       |
       v
token JWT
       |
       v
frontend


Después el frontend utiliza ese token para demostrar:

"Hola, soy un usuario que ya inició sesión."


------------------------------
CORS
------------------------------

CORS es una protección del navegador.

Nuestro frontend podría estar en:

http://localhost:5173

y nuestro backend:

http://localhost:8000


El navegador considera que son orígenes diferentes.

Por eso el backend tiene que decir:

"Sí, permito que localhost:5173 me haga peticiones."


------------------------------
SWAGGER
------------------------------

Swagger es probablemente el mejor amigo de la persona que haga el frontend.

FastAPI genera automáticamente documentación interactiva.

Normalmente está en:

http://localhost:8000/docs


Ahí podemos:

- ver endpoints;
- ver parámetros;
- ver JSON esperado;
- ver respuestas;
- probar peticiones;
- probar autenticación.

4. ¿QUÉ HACE CADA ARCHIVO/CARPETA?
============================================================


------------------------------
backend/app/
------------------------------

Aquí vive la aplicación FastAPI.

Esta es una de las carpetas MÁS IMPORTANTES.

Aquí encontraremos la lógica del backend.


------------------------------
backend/app/main.py
------------------------------

Es el punto de entrada de FastAPI.

Aquí se crea la aplicación.

Conceptualmente:

app = FastAPI()


También se registran diferentes rutas del proyecto.

Por ejemplo:

autenticación
usuarios
proyectos
carreras
departamentos
áreas temáticas
palabras clave
archivos
workflow
administración


Cuando Docker ejecuta:

uvicorn app.main:app

está diciendo:

"Busca app/main.py y ejecuta la aplicación FastAPI llamada app."


------------------------------
MODELOS
------------------------------

Los modelos representan las entidades de nuestra base de datos.

Por ejemplo:

Usuario
Proyecto
Carrera
Departamento


Conceptualmente:

MODELO PYTHON

Usuario
- id
- nombre
- email


se relaciona con:

TABLA POSTGRESQL

usuarios

id | nombre | email


------------------------------
ROUTERS
------------------------------

Los routers organizan los endpoints.

En vez de poner 300 endpoints en main.py podemos separarlos.

Por ejemplo:

auth
usuarios
proyectos
carreras
departamentos


Así el proyecto no termina siendo una sopa de código.


------------------------------
backend/alembic/
------------------------------

Aquí viven las migraciones.

Especialmente:

alembic/versions/


Cada archivo representa cambios realizados a la estructura de la base de datos.


------------------------------
backend/alembic.ini
------------------------------

Configuración principal de Alembic.


------------------------------
backend/alembic/env.py
------------------------------

Conecta Alembic con SQLAlchemy y nuestros modelos.

Gracias a esto Alembic puede saber:

"Estos son los modelos actuales."

y compararlos con:

"Esta es la base de datos actual."


------------------------------
backend/Dockerfile
------------------------------

Explica cómo construir el backend dentro de Docker.

El comando final ejecuta algo equivalente a:

uvicorn app.main:app --host 0.0.0.0 --port 8000


Esto significa:

Ejecuta FastAPI.

Escucha conexiones.

Utiliza el puerto 8000.


------------------------------
requirements.txt
------------------------------

Lista las dependencias de Python.

Por ejemplo:

FastAPI
SQLAlchemy
Alembic
psycopg
JWT
Argon2
etc.


Básicamente:

"Estas son las cosas que Python necesita instalar para que el proyecto no explote."


------------------------------
docker-compose.yml
------------------------------

Le dice a Docker cómo levantar los servicios.

IMPORTANTE:

Actualmente el docker-compose del proyecto levanta principalmente el BACKEND.

PostgreSQL todavía no está declarado como servicio dentro del Compose.

Esto es algo que convendría mejorar.


------------------------------
.gitignore
------------------------------

Le dice a Git:

"Estas cosas NO las subas."


Por ejemplo:

archivos temporales
entornos
secretos
.env.docker

7. VARIABLES DE ENTORNO
============================================================

Hay información que NO debemos escribir directamente en el código.

Ejemplo:

contraseña de PostgreSQL
JWT_SECRET
URL de base de datos


Para eso utilizamos archivos .env.


Existe:

backend/.env.example


Ese archivo es una PLANTILLA.


Podría contener algo parecido a:

DATABASE_URL=postgresql+psycopg://postgres:TU_PASSWORD@localhost:5432/project_repo_db

JWT_SECRET=CAMBIAME

JWT_ALGORITHM=HS256

ACCESS_TOKEN_EXPIRE_MINUTES=60

CORS_ORIGINS=http://localhost:5173


IMPORTANTE:

docker-compose.yml espera actualmente:

backend/.env.docker


Pero .env.docker está ignorado por Git.


Eso significa:

Cuando alguien hace git clone NO recibe ese archivo.


Tiene que crearlo.


¿POR QUÉ?

Porque no queremos subir secretos a GitHub.


REGLA:

.env.example
SÍ se sube.

.env.docker con secretos reales
NO se sube.

============================================================
20. CREAR UNA MIGRACIÓN
============================================================

ESTO NORMALMENTE ES TRABAJO DEL BACKEND.


Supongamos que modificamos un modelo.


Entonces:

docker compose exec backend alembic revision --autogenerate -m "agregar foto de perfil"


¿QUÉ HACE?

Alembic compara:

MODELOS ACTUALES

contra

BASE DE DATOS


y genera una propuesta de migración.


IMPORTANTE:

AUTOGENERATE NO SIGNIFICA:

"CONFÍA CIEGAMENTE EN MÍ."


La migración generada debe revisarse.


Después:

docker compose exec backend alembic upgrade head


Probamos todo.


Después subimos:

- cambio del modelo;
- archivo de migración.


A Git.


============================================================
21. OTROS COMANDOS DE ALEMBIC
============================================================

Ver migración actual:

docker compose exec backend alembic current


Ver historial:

docker compose exec backend alembic history


Actualizar:

docker compose exec backend alembic upgrade head


Retroceder una migración:

docker compose exec backend alembic downgrade -1


CUIDADO CON:

downgrade -1


Revertir una migración puede modificar/eliminar estructura y, dependiendo de la migración, afectar datos.


No usar a lo loco.

https://api.nuestroproyecto.com

Producción:

============================================================
25. CORS
============================================================

Frontend:

http://localhost:5173


Backend:

http://localhost:8000


Aunque ambos digan localhost, tienen puertos diferentes.


Para el navegador son ORÍGENES diferentes.


Entonces FastAPI necesita permitir:

http://localhost:5173


Para eso existe:

CORS_ORIGINS


Ejemplo:

CORS_ORIGINS=http://localhost:5173


Si CORS está mal configurado puedes encontrarte errores en el navegador aunque FastAPI funcione perfectamente.

39. ¿QUÉ DEBE ENTENDER LA PERSONA QUE DOCUMENTARÁ?
============================================================

IMPORTANTE:

Documentar NO significa escribir:

"main.py es el archivo main."

Gracias, Sherlock.


Una buena documentación debe explicar:


1. ¿QUÉ RESPONSABILIDAD TIENE?

Ejemplo:

main.py inicia FastAPI y registra las rutas de la aplicación.


2. ¿QUÉ RECIBE?

Ejemplo:

Un endpoint puede recibir un JSON con los datos de un proyecto.


3. ¿QUÉ HACE CON ESO?

Ejemplo:

Valida los datos, comprueba permisos y llama a la lógica correspondiente.


4. ¿QUÉ DEVUELVE?

Ejemplo:

Devuelve el proyecto creado en formato JSON.


5. ¿DE QUÉ DEPENDE?

Ejemplo:

El endpoint depende de:

- sesión de base de datos;
- usuario autenticado;
- modelos;
- servicios.


6. ¿QUÉ PUEDE FALLAR?

Ejemplo:

400 - datos incorrectos

401 - no autenticado

403 - no tiene permisos

404 - no existe

500 - backend dijo "hasta aquí llegué"

40. CÓMO DOCUMENTAR UN ENDPOINT
============================================================

NO hacer solamente:

POST /proyectos

"Crea proyectos."


Mejor:


ENDPOINT:

POST /proyectos


PROPÓSITO:

Crear un nuevo proyecto de investigación.


AUTENTICACIÓN:

Requiere usuario autenticado.


ENTRADA:

{
    "titulo": "...",
    "descripcion": "..."
}


PROCESO:

1. Comprueba autenticación.
2. Valida datos.
3. Crea entidad.
4. Guarda en PostgreSQL.
5. Devuelve resultado.


RESPUESTA:

{
    "id": 1,
    "titulo": "...",
    "descripcion": "..."
}


POSIBLES ERRORES:

400 - datos inválidos

401 - usuario no autenticado

403 - usuario sin permisos


Eso SÍ sirve como documentación.
